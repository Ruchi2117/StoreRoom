# V0.4 — durable scan and review history

## Purpose and workflow

V0.3 reviews were lost on refresh. V0.4 keeps each confirmed scan in a local SQLite
file so it can be reopened after refreshing the browser or restarting StoreRoom.
A scan remains an observation of visible packages in one photo, not reconciled
stock or the shop's complete inventory.

```text
Upload → existing prediction → review/correct → confirm
                                                 ↓
                                  SQLite scan + scan items
                                                 ↓
                                 Scan History → read-only review
```

The existing UI calls the same FastAPI backend. Prediction, class filtering, NMS
and counting are unchanged. Persistence happens only on confirmation.

## Local setup and initialization

From the repository root on the existing artifact-complete environment:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-api.txt
.\.venv\Scripts\python.exe -m uvicorn src.api:app --host 127.0.0.1 --port 8000
```

Open [StoreRoom](http://127.0.0.1:8000/). Use one process. Ctrl+C stops it.
See [inference setup](INFERENCE_PIPELINE.md) for restoring the frozen checkpoint
and CPU dependencies on a fresh clone. The model is still required for app startup.

The app automatically creates the directory and schema at startup, idempotently,
before serving requests. The default is `data/storeroom.db`, relative to the
repository root regardless of launch directory. To choose another local file:

```powershell
$env:STOREROOM_DB_PATH = 'data/my-scan-history.db'
.\.venv\Scripts\python.exe -m uvicorn src.api:app --host 127.0.0.1 --port 8000
```

Absolute local paths are also accepted through this server-side setting; paths
are not accepted from clients or returned in responses. `create_app` accepts
`database_path` for isolated tests. Changing the path selects a different database;
it does not migrate records. Keep the same file to retain history. The database
and SQLite sidecars are ignored by Git. It is durable data, not a disposable cache.

SQLAlchemy 2.0.54 is the only new direct runtime dependency. `src/storage.py`
contains table metadata, initialization and persistence operations. `create_all`
creates missing tables, not migrations of existing columns. Migrations can be
added here when the schema changes; none is needed for the first database schema.
There is no automatic schema repair or data deletion.

## Data model

```text
Scan (server-generated UUID, UTC created_at, status='confirmed')
 │
 ├── ScanItem (integer ID, scan_id foreign key)
 ├── ScanItem (class_id, class_name, predicted_count, confirmed_count)
 └── ... up to five unique classes
```

Items have a many-to-one relationship with the scan, uniqueness on
`(scan_id, class_id)`, and nonnegative integer count constraints. Foreign keys are
enabled for every SQLite connection. Names/IDs are validated against the existing
mapping before persistence. There are no catalog, user, SKU, shop or price tables.

Timestamps are stored as naive UTC datetimes and returned with the UTC timezone
restored. The UI formats them in the browser's local timezone. Each review retains
submitted predictions and confirmed counts, including items corrected to zero.
Empty supported-product reviews are allowed.

`ScanStore.confirm` uses one session transaction: insert/flush the parent,
insert/flush all items, serialize the result, then commit. The result is returned
only after commit. An item or commit failure rolls back the whole transaction.
Each request owns its session. Storage failures return generic HTTP 503 without
SQL, driver details or filesystem paths.

## API contracts

Existing `POST /predict` and `GET /health` remain available.

### POST /inventory/confirm

Request is unchanged from v0.3:

```json
{"items":[{"class_id":0,"class_name":"Red Bull","predicted_count":4,"confirmed_count":3}]}
```

Example response shape (ID/time below are illustrative):

```json
{
  "scan_id": "9bcd611d-fd65-4fd0-b37b-c999d49e5651",
  "created_at": "2026-09-19T00:00:00Z",
  "confirmed_at": "2026-09-19T00:00:00Z",
  "status": "confirmed",
  "persisted": true,
  "count_meaning": "visible_items",
  "items": [{"class_id":0,"class_name":"Red Bull","predicted_count":4,"confirmed_count":3}]
}
```

HTTP 200 is retained for compatibility. `confirmed_at` aliases `created_at` for
v0.3 clients. IDs are generated by the backend with UUID4. Malformed payloads,
unknown/mismatched classes, duplicate classes, extra fields and invalid counts
return 422. Counts are strict integers from zero through JavaScript's maximum safe
integer; booleans, strings and fractions are rejected.

Every successful POST creates a new scan. There is no idempotency protocol yet.
Do not automatically retry a confirmation whose response was lost: check history
first, since the commit might already have succeeded. Repeated UI submits are
disabled while saving; this is not cross-request deduplication.

### GET /inventory/scans?limit=20

Returns `{"scans":[{"scan_id":"...","created_at":"...","item_count":3}]}`.
Default 20; integer limits 1–100 are accepted, otherwise 422. Newest first, with
UUID ordering as a stable tie-breaker for identical timestamps. `item_count` is the
number of represented classes, **not packages**. Zero-corrected classes still count
as represented. Empty history is `{"scans":[]}`. The UI shows up to 20 recent scans.
No pagination or search is added.

### GET /inventory/scans/{scan_id}

Returns the complete saved confirmation object. A valid but nonexistent UUID returns
404; malformed UUIDs return 422. Lookups use bound SQLAlchemy parameters, not SQL
interpolation or filesystem paths. No edit/delete endpoint exists for old reviews.

## Frontend history

Choose **Scan History** from the header or receipt. Rows show date/time, represented
class count and **Open scan**. **Refresh history** reloads from SQLite. Saved reviews
display both counts read-only and label hidden inventory unknown. **Start a new
scan** clears the browser draft, not saved history. Opening history while reviewing
preserves the draft; **Back to current scan** restores it. Errors have retry/back
paths, and stale responses cannot restore a cancelled view.

## Image and provenance policy

History persists metadata/counts only. No images, image paths, model IDs or box data
are stored in SQLite. The current scan still displays its temporary annotation.
Saved reviews work independently of those files and state that historical photos
are not stored. No image/path parameter or binary database storage is introduced.

As in v0.3, the API validates submitted predicted counts but does not prove they
came from a specific inference result. These are human review submissions, not
authenticated or verified training/evaluation evidence.

## Tests and real smoke

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-ui-test.txt
.\.venv\Scripts\python.exe -m playwright install chromium
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Expected: 73 tests pass (62 retained/updated for persistence, 11 new). Tests use
temporary databases, never `data/storeroom.db`. New tests cover relationships,
initialization, timestamps, restart durability, multiple/zero items, a real item
constraint failure and rollback, ordering/limits, UUID errors/404, error hygiene,
and history browser interactions.

For a real product smoke (not accuracy evaluation):

1. Start the app and upload ordinary validation photo
   `data/yolo_v01/images/val/IMG_20181218_170247.jpg`.
2. Analyse once, change a count, confirm and note the returned scan ID.
3. Refresh, open Scan History, and find that scan.
4. Restart the backend with the same database. Reopen the scan and check both counts.
5. Start another non-test scan, confirm, and verify both appear newest first.
6. Stop the server cleanly.

The recorded run used that validation image twice, made two inference requests,
and passed refresh plus backend-restart checks. A separate ignored smoke database
kept the default local history unseeded. See [smoke evidence](../reports/v0_4_smoke.json)
and [results](../reports/V0_4_RESULTS.md).

## Limitations and next milestone

Five source classes; visible packages only; hidden stock unknown. The model remains
provisional and independent-scene generalization unverified. This local v0.4 SQLite
layer is not production infrastructure: no backup service, authentication, multi-shop
isolation, image archive or inventory synchronization. Losing the DB loses history.

Next major milestone: **traceable scan evidence**, linking retained photos and
server-side prediction records to human reviews. This would make corrections
auditable rather than relying on submitted counts. It is not implemented.

Transaction design follows SQLAlchemy's [session documentation](https://docs.sqlalchemy.org/en/20/orm/session_basics.html).
